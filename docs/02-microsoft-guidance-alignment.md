## 1. The 60-second interview answer

> "I didn't design the RAG pipeline from blog posts. I used Microsoft's **RAG solution design and evaluation guide** on the Azure Architecture Center as the backbone. It defines the phases: preparation, chunking, chunk enrichment, embeddings, information retrieval, end-to-end evaluation, and when to go agentic. Each phase of my project maps to one of them.
>
> For the code, I worked against the official Microsoft Learn docs for **Microsoft.Extensions.AI, VectorData, DataIngestion, Agent Framework and Aspire**. I had the **Microsoft Learn MCP server** connected to my AI coding tools, so every preview API was checked against the current docs *before* code was written. Every phase's handoff notes include a table of the pages consulted and what each one decided.
>
> My second rule was **built-in first**: if Microsoft.Extensions.AI, VectorData, DataIngestion, Microsoft.ML.Tokenizers or the Agent Framework already has the abstraction, I use it directly. Every custom type left in the repo has a one-line "why no built-in fits" in an audit table. That rule deleted about a dozen hand-rolled interfaces:
> - retrieval *is* MEVD's `IVectorSearchable<T>`;
> - embeddings are two keyed `IEmbeddingGenerator` pipelines;
> - the chat API is **AG-UI** served by Agent Framework hosting, with sessions in an `AgentSessionStore` and guardrails as agent middleware;
> - LLM JSON comes from `GetResponseAsync<T>`, caches from `UseDistributedCache`, and token counts from `Tokenizer.CountTokens`.
>
> Three examples where the docs changed my design:
> - **I first wrapped MEDI in my own abstractions.** That meant my own sources, reader resolver, writer, cleaner interfaces, fingerprint contributors and counters. After re-reading Learn, I used `IngestionPipeline<string>` and `VectorStoreWriter<string>` directly: fewer classes, same behavior. `ProcessAsync` takes files only, so I stage blobs to a temp folder, and that's the only glue left.
> - I initially assumed `VectorStoreWriter<T>` couldn't hold typed metadata, because its Learn page says it uses a "default schema". Reading its source, linked from that page, showed that chunk metadata becomes columns (including string arrays, which the Postgres connector supports), and that `IncrementalIngestion` does upsert-then-delete. So I adopted it, and I store only the cleaned chunk.
> - The PgVector connector docs list hybrid search as unsupported, so I built hybrid search myself with Postgres full-text plus vectors and Reciprocal Rank Fusion. I put it behind MEVD's own `IKeywordHybridSearchable<T>`, so callers still only see built-in types.
>
> The guide also has a section called *'Calculate the cost of augmenting'*. When I did that math for LLM-generated chunk metadata on a CPU laptop (about 1,500 chunks × 10–20 s, so 4–8 hours per index), I shipped the **cleaning** half of enrichment first and kept the augmentation design ready."

**Be ready to say how the lookups happened.** AI coding agents did the searching under your direction, using the Microsoft Learn MCP tools (`microsoft_docs_search`, `microsoft_code_sample_search`, `microsoft_docs_fetch`). The specs *required* it, and the notes files are the evidence. You reviewed and decided.

## 2. Method: how the docs were consulted

**Rule: Microsoft Learn is the source of truth.** For Microsoft SDK and API behavior, and for RAG concepts, terminology and phase order, current Microsoft Learn documentation overrides the specs, `docs/02`, blog posts and an agent's prior knowledge. Every spec's §0 states this. Conflicts are logged, not silently resolved. Project-specific design (names, contracts, config) stays as specified unless Learn shows it's impossible.

1. **Design (planning sessions).** The architecture was drafted after reading the Microsoft RAG guide and the SDK overview pages listed in §4. Design decisions that came from a page are recorded in `docs/01-architecture-and-design.md` §9 (the decision log).
2. **"Verify before you code" rule.** Every phase spec (`docs/specs/phase-NN-*.md` §0) instructs the implementing agent to verify preview or unfamiliar APIs with the Microsoft Learn MCP server before using them. These packages are preview or fast-moving: DataIngestion, Agent Framework, Aspire 13 hosting APIs.
3. **Evidence log.** Every spec's §11.0 requires a table in the phase notes: *URL → what was checked → decision in code*. It also records where docs and reality disagreed.
4. **Review loop.** After specs were written, independent reviewer agents cold-read them and challenged API claims against the docs. Fixes were applied before implementation. For example, the reviewers found the Aspire CLI's `wait` default of "healthy", which never completes for a one-shot job.

## 3. Alignment with Microsoft's RAG solution design guide

Source: [Design and develop a RAG solution](https://learn.microsoft.com/azure/architecture/ai-ml/guide/rag/rag-solution-design-and-evaluation-guide), the introduction to the series.

The guide's data pipeline is **chunk → enrich → embed → persist**. Its application flow is **query → orchestrator → search → top-N into the prompt → model**. Ours:

```
EDGAR HTML → IngestionInit (init job: download + upload, then exit) → Blob
you → POST /api/index → [Indexing Function: MEDI IngestionPipeline<string> over staged files]
   read & clean HTML → chunk (HeaderChunker) → clean (enrichment) → MEDI VectorStoreWriter<string>: embed + persist the cleaned chunk to pgvector
User → AgentClient.Cli (AGUIChatClient) → AG-UI /agents/{name} → [API: MAF hosted agent + TextSearchProvider / tools] → IVectorSearchable (vector / hybrid / rerank) → top-N + citations → model
```

## 5. Where we deliberately deviate, and the reasons

| Guidance | Our choice | Reason |
|---|---|---|
| The reference architecture uses **Azure AI Search** | **Postgres + pgvector** | The project must run fully locally for demos. The *concepts* carry over (vector index, hybrid, reranking ≈ semantic ranking). The built-in `IVectorSearchable<T>` contract keeps the search engine swappable: any MEVD connector, Azure AI Search included, implements it. |
| Cleaning: remove stop words | Not applied | The guide says to test first. Transformer embedding models use function words, and "not" changes meaning. |
| Cleaning: fix spelling | Not applied | Filings are professionally edited; auto-correct risks corrupting tickers, product names and GAAP terms. |
| Cleaning: normalise text (numbers to words, expand abbreviations) | Not applied | It would destroy financial figures and terms like "MD&A" that users search for. |
| Cleaning: lower-casing | Available, **off** by default | Pending measurement. It has to be symmetric (documents and queries), and changing it re-indexes via the fingerprint. |
| Keep the original chunk in an extra field (optional in the guide) | Not applied: **only the cleaned chunk is stored** | What the model reads and cites equals what was matched; cleaning is conservative (no words, numbers or tickers removed); a single text column lets us use the SDK's `VectorStoreWriter<string>` unchanged. Lower-casing, if enabled, happens only inside the embedder, never in stored text. |
| Augment with LLM-generated metadata | Deferred | Cost on CPU (§1); design ready in Phase 14. |
| Evaluate embedding models | Not yet | Time-boxed; the extension path is documented (§3). |
| Measure utilisation | Not yet | Not among our evaluator set; candidate for a custom evaluator. |

## 6. Likely interview follow-ups

- **"Why not Azure AI Search, if you followed Microsoft's guide?"** The guide is about the *phases*; Azure AI Search is its reference engine. I needed offline demos, so pgvector. Retrieval is the built-in MEVD `IVectorSearchable<T>`, so switching means registering a different connector's collection. The hybrid and reranking decorators mirror AI Search's hybrid plus semantic ranking.
- **"What's the difference between cleaning and augmenting?"** Cleaning changes what gets *embedded*, to improve vector matches. Augmenting adds *new fields* (summary, keywords, questions) for filtering and keyword search. We store only the cleaned chunk, so what's embedded is what's cited. The guide's "keep the original too" field is optional, and we chose not to.
- **"Why so few custom classes?"** Built-in first. There's an audit table (docs/02 §5.8) with every custom type and why no built-in fits. Examples: the PgVector connector has no hybrid search, MAF has no durable session store, and no library ships Hit@k/MRR.
- **"How did you know the APIs were right if they're in preview?"** Every spec forced a Learn lookup before coding, and the notes log it. Where reality differed (renamed APIs, a changed signature), the notes say so.
- **"What would you do next, per the guide?"** Measure lower-casing and an alternative embedding model in the eval matrix; add LLM augmentation for the most-queried sections; add a utilisation metric.
